# mpei-mail-api — дизайн

Дата: 2026-09-04

## Задача

HTTP-сервис на Go, который ходит в почту МЭИ (`mail.mpei.ru`) и отдаёт письма в виде
JSON. Потребитель — шедулерная таска в Claude, которая по расписанию дёргает ручку,
смотрит новые письма и решает, что с ними делать. Сервису не нужен UI, не нужна
многопользовательность и не нужна отправка почты: SMTP у МЭИ и так недоступен.

## Разведка сервера (сделана до дизайна)

С машины разработки прощупан `mail.mpei.ru`:

| Порт | TCP | TLS-handshake |
|---|---|---|
| 993 (IMAPS) | открыт | обрывается, сертификат не отдаётся |
| 995 (POP3S) | открыт | обрывается, сертификат не отдаётся |
| 443 (HTTPS) | открыт | ОК, сертификат `CN=*.mpei.ru` |

TCP-коннект на 993/995 проходит, но TLS немедленно получает EOF. Причину с этой
машины различить нельзя: это либо фильтрация по IP/сети, либо IMAP на сервере
выключен администраторами МЭИ, несмотря на опубликованные настройки.

Дополнительно установлено, что `mail.mpei.ru` — это Microsoft Exchange, и по 443 он
отдаёт живые эндпоинты с Basic-аутентификацией:

```
/EWS/Exchange.asmx            401 WWW-Authenticate: Basic Realm="mail.mpei.ru"
/Microsoft-Server-ActiveSync  401 Basic
/mapi/emsmdb                  401 Basic
```

Отсюда главное архитектурное следствие: **протокол доступа к почте — не константа,
а сменная деталь.** Дизайн изолирует его за интерфейсом, чтобы замена IMAP на EWS не
трогала ни ручки, ни JSON-контракт, ни шедулерную таску.

## Выбранный подход

Рассматривались три варианта:

- **A. Только IMAP.** Меньше всего кода, ровно по исходному ТЗ. Риск: если хост
  деплоя видит 993 так же, как машина разработки, сервис не заведётся вообще, и
  выяснится это только на проде.
- **B. Только EWS поверх 443.** Максимальный шанс заработать откуда угодно, но в Go
  нет живой EWS-библиотеки: SOAP-конверты (`FindItem`/`GetItem`/`UpdateItem`) и
  разбор XML пишутся руками, объём работ втрое больше.
- **C. Интерфейс `Source` с выбором реализации.** Общие HTTP-слой, JSON-модель и
  авторизация; протокол за интерфейсом.

**Принят вариант C** со следующей тактикой: интерфейс и HTTP-слой пишутся сразу,
реализуется сначала IMAP как заведомо более дешёвый, и первым шагом реализации идёт
проверка 993 из целевой среды. Если 993 там живой — EWS-реализация не пишется вовсе
(YAGNI). Если мёртв — добирается `ewssrc`, и ничего вокруг переписывать не нужно.

Среда деплоя на момент написания спеки не выбрана. Это и есть причина, по которой
развилка оставлена открытой, а не срезана в пользу A.

## Архитектура

Один Go-бинарь, три слоя, зависимости направлены строго внутрь:

```
cmd/mpei-mail-api/main.go     конфиг из ENV, сборка зависимостей, http.Server,
                              graceful shutdown
internal/httpapi/             роутинг, middleware, JSON-модель,
                              маппинг доменных ошибок в HTTP-коды
                              — не знает про IMAP
internal/mail/                доменные типы + интерфейс Source
                              — не знает про HTTP
internal/mail/imapsrc/        реализация Source на go-imap/v2
internal/mail/ewssrc/         вторая реализация; пишется, только если 993 мёртв
```

Граница между слоями:

```go
type Source interface {
	List(ctx context.Context, q ListQuery) ([]Message, error)
	Get(ctx context.Context, uid string) (*MessageFull, error)
	MarkSeen(ctx context.Context, uid string) error
	Ping(ctx context.Context) error
}
```

`uid` — строка, а не `uint32`. В IMAP это число, но в EWS `ItemId` — base64-строка.
Если зашить IMAP-овский тип в интерфейс и в JSON, вторая реализация сломает публичный
контракт ручки и шедулерную таску придётся переписывать. `imapsrc` парсит строку в
`imap.UID` внутри себя.

`httpapi` принимает `Source` как зависимость и ничего не знает о том, какая
реализация подставлена. `main` выбирает реализацию по `MAIL_SOURCE`.

### Зависимости

- `github.com/emersion/go-imap/v2` — IMAP-клиент. Именно v2: API — `imapclient.DialTLS`,
  `Login().Wait()`, `Select`, `Search`, `Fetch`, `Store`.
- `github.com/emersion/go-message` — разбор MIME и декодирование кодировок.
  Нужен потому, что windows-1251 и KOI8-R в заголовках у российских отправителей
  встречаются регулярно.

Всё остальное — stdlib. Роутинг на `net/http.ServeMux`: с Go 1.22+ он умеет
`GET /messages/{uid}`, HTTP-фреймворк не нужен.

## Контракт ручек

```
GET  /healthz                                    без авторизации
GET  /messages?limit=&unseen=&since=&mailbox=
GET  /messages/{uid}?mailbox=
POST /messages/{uid}/seen
```

Авторизация: заголовок `Authorization: Bearer <API_TOKEN>` на всех ручках,
кроме `/healthz`.

### GET /messages

Параметры: `limit` (по умолчанию 20, максимум 100), `unseen` (bool),
`since` (RFC3339 или `YYYY-MM-DD`), `mailbox` (по умолчанию `INBOX`).

```json
{
  "messages": [
    {
      "uid": "12345",
      "from": {"name": "Иванов И.И.", "email": "ivanov@mpei.ru"},
      "to": [{"name": "", "email": "student@mpei.ru"}],
      "subject": "Расписание пересдач",
      "date": "2026-09-03T14:21:00+03:00",
      "seen": false,
      "has_attachments": true,
      "snippet": "Уважаемые студенты, пересдача по..."
    }
  ],
  "count": 1
}
```

`snippet` — первые 300 символов `text/plain` после декодирования. Он существует,
чтобы шедулерная таска в большинстве случаев решала «интересно / не интересно» по
одному запросу, не ходя за телом каждого письма.

`count` — количество элементов в `messages`, а не общее число писем в ящике.
Пагинации нет: потребителю нужны последние N писем, а не обход всего ящика.

### GET /messages/{uid}

Возвращает поля списка плюс `cc`, `text`, `html` и
`attachments: [{name, mime, size}]`. Содержимое вложений не отдаётся — только
метаданные.

Читает через `BODY.PEEK[]` и **не помечает письмо прочитанным**. Пометка происходит
только по явному `POST /messages/{uid}/seen`. Иначе шедулер незаметно менял бы
состояние живого почтового ящика пользователя.

### POST /messages/{uid}/seen

Возвращает `204 No Content`. Идемпотентна: повторный вызов на уже прочитанном письме
успешен.

### GET /healthz

```json
{"status": "ok", "source": "imap", "upstream": "ok"}
```

Возвращает `200`, пока жив процесс. Доступность МЭИ выражена отдельным полем
`upstream` (`ok` / `fail`), а не кодом ответа: если завязать код на доступность
`mail.mpei.ru`, k8s-liveness начнёт перезапускать под из-за чужой недоступной почты,
а рестарт её не чинит. Результат проверки апстрима кэшируется на 30 секунд, чтобы
частые опросы health не превращались в шторм IMAP-логинов.

### Ошибки

Единый конверт: `{"error": {"code": "...", "message": "..."}}`.

| Код | HTTP | Когда |
|---|---|---|
| `unauthorized` | 401 | нет или неверный Bearer |
| `bad_request` | 400 | некорректные `limit`, `since` или `uid` |
| `message_not_found` | 404 | UID не найден в mailbox |
| `upstream_unavailable` | 502 | не удалось подключиться или залогиниться в МЭИ |
| `upstream_timeout` | 504 | МЭИ не ответил за отведённый таймаут |
| `internal` | 500 | всё непредусмотренное, включая панику в хендлере |

Разделение 502 и 504 функционально: шедулерной таске по ним надо вести себя
по-разному. 504 имеет смысл повторить сразу, 502 (в частности «IMAP выключен
администраторами») повторять бессмысленно.

## Поток данных

```
List:      DialTLS → Login → Select(mailbox, ReadOnly=true)
           → Search(criteria)                        # unseen / since → набор UID
           → последние N UID
           → Fetch(Envelope + Flags + BodyStructure + префикс текстовой части)
           → Logout

Get:       DialTLS → Login → Select(mailbox, ReadOnly=true)
           → Fetch(BODY.PEEK[])
           → go-message: text/plain, text/html, метаданные вложений
           → Logout

MarkSeen:  DialTLS → Login → Select(mailbox, ReadOnly=false)
           → Store(UID, +FLAGS \Seen)
           → Logout
```

Для сниппета в `List` тянется префикс текстовой части, а не письмо целиком: иначе
список из 20 писем с вложениями превращается в мегабайты трафика ради трёхсот
символов текста. Конкретно:

- Номер части определяется по `BodyStructure`: ищем первую часть с `text/plain`, при
  её отсутствии — первую `text/html` (тогда теги вырезаются при формировании
  сниппета). У не-multipart письма это `BODY.PEEK[TEXT]`. Слепо брать часть `1`
  нельзя: в `multipart/alternative` порядок частей задаёт отправитель.
- Размер префикса — 2048 байт, не 512. Кириллица в UTF-8 занимает два байта на
  символ, а тело вдобавок приходит в quoted-printable или base64, поэтому 512 байт
  до декодирования не дают требуемых 300 символов после.

### Стратегия подключений

**Коннект на запрос, без пула.**

Альтернатива — долгоживущий коннект с NOOP-keepalive и реконнектом — экономит
300–600 мс на TLS и LOGIN, но приносит целый класс состояний: протухший коннект,
гонка между `Select(ReadOnly=true)` в `List` и `Select(ReadOnly=false)` в `MarkSeen`,
и Exchange всё равно рвёт простаивающие IMAP-сессии по собственному таймауту. Для
таски, которая дёргает ручку раз в несколько минут, сэкономленные полсекунды никто не
наблюдает.

Зафиксированный риск: типичный проход шедулера — это `List`, затем несколько `Get` и
несколько `seen`, то есть до десятка LOGIN подряд. Если Exchange МЭИ настроен на
троттлинг аутентификаций, упрёмся именно в это. Проверить заранее нельзя — 993 с
машины разработки недоступен.

Триггер для смены решения: сервер начинает отклонять логины под нагрузкой. Лечение —
ленивый единственный коннект под мьютексом с идловым TTL 2 минуты; это примерно 40
строк внутри `imapsrc` и не задевает ни интерфейс `Source`, ни контракт ручек.
Закладываться на это заранее не будем.

### Таймауты

| Что | Значение |
|---|---|
| Контекст запроса | 30 с (`REQUEST_TIMEOUT`) |
| Dial | 10 с |
| `ReadHeaderTimeout` | 5 с |
| `WriteTimeout` | 60 с |

Контекст запроса пробрасывается в `Source` и рвёт IMAP-сессию, если клиент отвалился.

## Конфигурация

| ENV | Дефолт | Обязательна |
|---|---|---|
| `MPEI_USER` | — | да |
| `MPEI_PASS` | — | да |
| `API_TOKEN` | — | да |
| `LISTEN_ADDR` | `127.0.0.1:8080` | нет |
| `MAIL_SOURCE` | `imap` | нет |
| `IMAP_ADDR` | `mail.mpei.ru:993` | нет |
| `REQUEST_TIMEOUT` | `30s` | нет |

Дефолт `LISTEN_ADDR` — `127.0.0.1`, а не `0.0.0.0`: наружу сервис выставляется
осознанно, через reverse-proxy или явную смену переменной.

## Безопасность

- **Пустой `API_TOKEN` — процесс не стартует.** Иначе однажды ручка с доступом к
  почте окажется выставлена без авторизации и это останется незамеченным. Отказ
  стартовать громче, чем тихий дефолт.
- Сравнение токена через `subtle.ConstantTimeCompare`.
- В логи пишутся `uid`, количество писем, длительность, код ошибки. Пароль и токен —
  никогда, в том числе внутри текстов ошибок, приходящих из библиотеки: ошибки
  апстрима перед логированием оборачиваются в доменные.
- TLS с обычной верификацией сертификата. `InsecureSkipVerify` не используется:
  у `*.mpei.ru` валидный сертификат, это проверено.

## Тестирование

Объём тестов сознательно урезан до минимума, полезного при собственном использовании:

- **Контрактные тесты `internal/httpapi` на фейковом `Source`** — коды ответов,
  конверт ошибок, авторизация, валидация `limit` и `since`, дефолты. Без сети,
  выполняются за миллисекунды.
- **Интеграционная проверка `imapsrc`** под build-тегом `integration`, креды берутся
  из ENV, тест скипается при их отсутствии. Это первый практический ответ на вопрос,
  жив ли 993 из целевой среды.

Сознательно не делаются: набор `.eml`-фикстур на MIME-разбор и curl-смоук по ручкам.
Принятое следствие: баги с кодировками заголовков (windows-1251 в теме письма)
всплывут на реальных письмах и будут чиниться по факту.

## Артефакт сборки

Статический бинарь (`CGO_ENABLED=0`) и Dockerfile на distroless. Пока среда деплоя не
выбрана, systemd-юнит и манифесты k8s не пишутся.

## Что вне объёма

- Отправка почты. SMTP у МЭИ недоступен.
- Скачивание содержимого вложений — только метаданные.
- Многопользовательский режим: одна учётная запись на процесс, креды из ENV.
- Хранение состояния, база данных, очередь. Состояние «прочитано» живёт на сервере
  МЭИ в виде флага `\Seen`.
- Вебхуки и IMAP IDLE. Потребитель — шедулер, он опрашивает сам.
